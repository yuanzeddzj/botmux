# 群话题唯一负责人

在同一台 BotMux 主机上，为参与协作的每个 bot 设置 `exclusiveTopicOwner: true`。
负责人以群 ID 和话题根消息 ID 共同寻址，各话题独立并行。

首次明确 @ 一个 bot 选择负责人。后续同一话题的普通回复无需 @，只交给负责人。
再次明确 @ 另一个 bot 立即改变选择；待旧执行停止并得到确认后，新负责人开始处理。
同时 @ 多个 bot 时不创建多个执行。原有消息权限仍然执行。

负责人记录存于共享数据目录的 `topic-owners/`。选择记录和执行记录使用不同文件锁：
选择不等待耗时的执行准备，执行锁覆盖旧进程停止和新回合的入站准备。
更换负责人增加 epoch；同一负责人续话保持 epoch。迟到事件不能覆盖较新的选择。

延迟输入、启动、IPC 重试和重启同时检查选择与完成交接的执行记录。
异步上下文保留原 epoch，避免 A → B → A 把旧 A 的回调当成新授权。
旧会话保留历史并休眠，以后重新接手时从历史恢复。

交接走经过主机 HMAC 认证的 `/api/topic-ownership/revoke`。
只停止目标话题的本机受管进程和确切的持久后端，不关闭整台主机的执行名额。
本机 PTY 需验证 worker 和已证明身份的 CLI 退出；持久后端还需验证确切 backing 已消失。
Linux 在交接时将确切话题的生产者移入独立 user systemd scope，确认完整成员后停止该 scope；
快照后新产生的后代也继承该 scope，不能逃过停止。cgroup v1/v2 均检查实际退出。
其他主机需要能够稳定停止并校验整个已捕获进程树；tmux 自动续跑导致停止不可证时拒绝交接。
无法验证退出、外部采用的进程或不支持停止的远程执行拒绝交接，不启动第二个 bot。
某个离线 bot 没有目标话题的持久成员记录时，独立话题仍可工作。

升级时所有协作 bot 都需要运行支持本协议的版本，并使用同一个数据目录。
已有话题第一次使用时，以原生话题历史中可验证的明确 bot mention 恢复归属。
无法证明历史归属时，需要一次明确 @。单聊行为由原单聊配置决定。

验证涵盖真实 dispatcher、跨进程文件锁、交接中途改选、失败恢复、旧 epoch、
物理退出、普通输入重投和不同话题并行。
